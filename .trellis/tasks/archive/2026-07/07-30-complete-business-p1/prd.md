# 完成商城 P1 业务能力与验收闭环

## Goal

在现有 P0 和运营后台能力之上，完成商城 P1 的可靠性与质量闭环：让 B 池冻结积分以可审计批次按 FIFO 释放，确保订单完成、售后冲正、规则版本和任务重放保持一致；补足 P1 应用服务与投影任务的自动化测试、运行验收和开发规范状态。

## What I already know

- 分类、商品、多 SKU、内容运营、库存流水、会员管理、订单检索/导出/备注/批量发货、仪表盘、通知和前后台页面已经存在。
- 原始 PRD 明确要求 B 池按版本化配置和先进先出批次释放。
- 当前 `OutboxProjectionProcessor` 仅从 `ledger_account.frozen_points` 汇总余额扣减，没有冻结批次事实，也无法证明 FIFO。
- 可靠性投影、自动收货和无业绩降级目前缺少直接自动化测试。
- `.trellis/spec/backend/` 与 `.trellis/spec/frontend/` 已经按实际代码填写，但初始化任务仍显示未完成。

## Requirements

- 新增只追加的 B 池冻结批次模型，记录账户、来源积分分录、来源订单、生成规则版本、初始积分、剩余积分和状态。
- 第 6 名及以后产生 B 池积分时，必须幂等创建一个冻结批次。
- 符合条件的复购订单完成后，按批次创建时间和 ID 先进先出释放；单次释放可跨多个批次。
- 每一段批次释放都生成独立积分流水，并关联复购订单、释放规则版本和原冻结分录。
- 每一段释放额外保存释放流水到实际冻结批次的明细映射，Flyway 为升级前未冲正流水反推相同关系。
- 普通商品订单、金额未达门槛、未完成订单、无冻结余额和重复事件不得释放积分。
- 直属业绩订单售后完成时关闭其尚未释放的冻结批次；已经释放的部分继续通过反向流水从可用积分冲正。
- 复购订单售后完成时恢复对应批次的剩余积分，且反向流水只执行一次。
- 批次余额、汇总账户余额和积分流水必须在同一事务内更新，冲突时整体回滚。
- 增加投影、FIFO、跨批次释放、重复事件、售后恢复/关闭、无业绩降级和主要 P1 应用服务测试。
- 更新架构、数据库、运行说明和 P1 验收证据；保持演示积分不可提现、不可转账、不可兑换现金。
- 将已实际完成的 Trellis 开发规范初始化清单标记完成并归档。

- [x] 普通购买、金额不足和非完成订单不会释放 B 池积分。
- [x] 复购售后冲正恢复原先消耗的批次；直属业绩售后关闭未释放批次，账户与批次合计一致。
- [x] 每条释放流水可追溯复购订单、释放规则版本和原冻结分录。

## Definition of Done

- 领域/应用/基础设施/接口依赖方向符合 DDD 与凤凰架构约束。
- 数据库迁移仅前向追加，不修改已发布迁移。
- 事务、幂等键、并发锁、规则版本与售后冲正行为有自动化证据。
- 不引入在线支付、真实分红、代付、提现或现金等价物兑换。
- 所有质量门禁通过，Trellis P1 任务状态与实际完成状态一致。

## Technical Approach

- 使用 Flyway V9 新增 `ledger_frozen_batch`、`ledger_frozen_release` 和 `ledger_frozen_release_item`，将账户汇总余额保留为快速投影，将批次与释放明细作为 B 池顺序、剩余量和消费来源事实。
- `DIRECT_REFERRAL_AWARD` 的冻结部分创建来源批次；`FROZEN_POINTS_RELEASED` 按批次拆分分录，通过 `original_entry_id` 与释放明细共同关联来源冻结分录。
- Outbox inbox 幂等继续作为事件级防重；批次唯一键与积分流水幂等键提供业务级二次防线。
- 售后投影在生成反向流水前锁定并恢复/关闭相关批次，使批次事实与账户汇总在同一事务中收敛。
- 以基础设施单元测试验证投影编排，以空库 MySQL 运行验收验证 SQL、迁移和真实事务。

## Decision (ADR-lite)

**Context**：仅保存账户冻结总额无法证明 FIFO，也无法在跨批次释放和售后冲正后解释每一分积分来自哪里。

**Decision**：增加冻结批次事实表，积分账户继续作为可重建汇总投影；释放流水逐批次关联原冻结分录。

**Consequences**：账本可审计性和冲正准确性提高；投影逻辑需要同时维护批次和汇总余额，但全部位于同一事务且可通过 outbox/inbox 重放。

## Out of Scope

- 在线支付、提现、积分转账、现金兑换和真实资金结算。
- 多级团队计酬或超过直属一层的奖励。
- 真实微信、短信、邮件供应商的生产凭据申请。
- 微服务拆分和真正的多租户计费系统。
