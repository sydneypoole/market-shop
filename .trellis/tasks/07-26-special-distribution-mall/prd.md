# 特殊分销商城 MVP

## Goal

从空仓库开始建设一套同时服务网页端与 H5 的特殊分销商城。后端采用 Spring Boot、MyBatis-Flex、Sa-Token、Redis、Hutool、MySQL 与 Flyway，业务设计遵循 DDD 与凤凰架构约束；商品、会员升级任务、金额门槛、积分池和资格降级规则由运营后台动态配置。

## What I already know

- 当前仓库没有业务代码，只有 Trellis 项目管理与待完善的 backend/frontend 规范骨架。
- 客户端至少包含网页端与 H5；需要一个运营管理后台。
- 用户给出的会员链路包含“体验官 → 超级会员 → 分红会员”。
- 体验官规则：消费 298 元成为体验官；绑定超级会员专属码并消费 1998 元后，后台审核通过可成为超级会员。
- 超级会员规则：消费 1998 元后具备升级条件，并拥有专属二维码；起盘阶段可配置管理账号用于管理后台。
- 分红会员规则：超级会员通过专属二维码发展新用户；完成 5 名新用户绑定并完成 1998 元消费后具备分红会员资格，从第 6 名开始计算积分。
- 图片示例中，每名 1998 元新会员产生 320 积分，并拆分进入 A 直推积分池与 B 复购积分池；连续 5 个月无业绩时降级为超级会员。图片中的部分细分分配文字仍需业务确认。
- 商城不收取用户在线支付；用户与直属上级在线下完成收付款，系统流程为“用户提交订单 → 直属上级确认已线下收款 → 后台审核 → 发货 → 用户确认收货”。
- 参考产品为 `https://shop.xingkehui.com.cn/h5/#/pages/index/index`，用于归纳商城页面与功能，不代表复制其品牌、素材或受版权保护内容。

## Assumptions (temporary)

- 首版采用模块化单体，而不是直接拆微服务；领域边界与事件接口预留未来拆分能力。
- 运行基线暂定 Java 21 + Spring Boot 4.1.x；第三方 starter 在正式编码前用最小启动工程验证兼容性。
- 金额使用整数分存储，积分使用定点数或整数，禁止浮点计算。
- 升级、降级、佣金/积分入账均以可审计流水和规则快照为准；规则修改不追溯已结算订单。
- “上级”暂定义为用户通过邀请码或二维码绑定的直属邀请人；用户向该上级线下付款，上级只能处理其直属下级提交的订单。
- 本任务交付为规则演示与技术验证用途；可以模拟截图中的会员链路和 A/B 积分池，但不得启用生产资金结算、提现或现金等价物兑换。
- 微信内 H5 使用公众号网页授权，电脑网页使用开放平台网站应用扫码登录；两种身份优先通过同一开放平台主体下的 UnionID 关联到统一商城账号。

## Requirements

- 前后端分离，API 同时支持网页端与 H5。
- 商城端采用精品零售视觉体系，在保持购物路径简洁清晰的前提下，使用原创商品主视觉、实验性但可读的排版、细腻动效和响应式媒体编排；首页、商品详情、购物车与结算必须具备一致的商城识别度。
- 商城端动效遵守 `prefers-reduced-motion`，商品图片提供语义化替代文本、加载占位和失败兜底，桌面与 H5 均不得因视觉效果遮挡价格、库存或购买动作。
- 本轮交付完整可运行 MVP，包括 Spring Boot 后端、响应式网页/H5 商城、独立运营后台、MySQL/Redis/私有对象存储本地环境、Flyway 迁移、自动化测试、API 文档和部署运行说明。
- 仓库提供一键式本地启动方式；基础设施通过容器编排启动，应用支持开发环境分别启动和演示环境整体启动。
- 提供用户认证、微信注册与登录、会员关系绑定、商品浏览、购物车、线下收款报单审核、发货、收货确认和售后基础能力。
- 微信内 H5 支持公众号网页 OAuth 自动注册/登录，电脑网页支持开放平台网站应用扫码注册/登录；非微信环境的移动浏览器首版提示用户在微信中打开或展示登录二维码。
- 微信授权回调必须由后端使用临时授权码换取并校验微信身份，前端不得提交 OpenID/UnionID 直接换取商城登录态；校验成功后由 Sa-Token 签发商城会话。
- 微信外部身份按渠道、AppID 与 OpenID 唯一保存，UnionID 作为跨公众号/网站应用的账号关联依据但允许为空；会员、订单与邀请关系统一引用商城用户 ID。
- 微信 OAuth `state` 使用 Redis 中的一次性随机挑战并绑定渠道、白名单回跳地址和签名邀请上下文；挑战过期、重复消费或参数不匹配时拒绝登录。
- 首次可信微信授权创建会员账号必须幂等；重复回调不得创建重复用户、重复绑定邀请人或改变既有上下级关系。
- 除系统初始化的根会员/管理账号外，首次微信授权注册必须携带有效且未过期的邀请链接或专属二维码；没有邀请上下文时可以完成微信身份校验，但不能创建商城会员账号。
- 邀请人必须存在、账号状态正常且在绑定时拥有邀请权限；默认只有有效的超级会员或分红会员可以生成邀请链接/二维码。
- 新会员创建与直属上级绑定在同一事务中完成。一个会员只能绑定一个直属上级，绑定后普通用户和后台均不得直接修改；禁止自我邀请、重复绑定和形成关系环。
- 邀请上下文只保存不可篡改的邀请标识，回调时由后端重新查询并校验邀请人当前状态；失效、伪造或已撤销的邀请链接不得注册会员。
- 微信 AppSecret、授权令牌及换取身份的请求只存在于服务端配置和服务端链路，不写入前端包、日志或业务表明文字段。
- 运营后台账号、凭据和 RBAC 权限体系与商城会员身份分离，使用独立登录类型和会话；会员等级、邀请资格与积分状态不会自动授予任何后台权限。
- 系统初始化 1 个超级管理员，并支持通过安全初始化配置创建 3 个起盘运营账号；初始凭据不以明文提交到仓库，首次登录必须修改临时密码。
- 起盘运营账号可以显式关联一个商城超级会员，用于业务展示和起盘关系，但关联只用于审计与业务引用，后台权限仍完全由角色和权限项决定。
- 后台默认角色至少覆盖超级管理员、订单审核、履约发货、商品运营、会员运营和只读审计；超级管理员可按最小权限原则组合角色、停用账号和重置凭据。
- 超级管理员创建账号、角色授权、账号关联、停用、解锁和凭据重置均为敏感操作，必须二次校验当前管理员身份并记录不可变审计日志。
- 提供会员等级、升级任务、邀请二维码、分销关系、积分池、资格降级和结算流水。
- 演示环境允许配置“体验官 → 超级会员 → 分红会员”、发展人数门槛、第 6 名起计分和 A/B 积分池规则。
- 默认积分规则为：前 5 名完成任务的直属新会员只用于取得分红会员资格，不产生积分；从第 6 名开始，每名直属新会员完成配置的 1998 元任务后产生 320 演示积分，其中 A 直推池 160 分立即成为可用积分，B 复购池 160 分以冻结批次入账。
- B 池冻结积分仅在直属上级自己的符合条件复购订单完成后释放；复购商品范围、订单金额门槛、单次固定/按比例释放方式、释放上限及先进先出顺序由后台版本化配置。
- A/B 积分计算使用新会员订单完成时生效的规则快照；规则变更不追溯已生成的积分批次，任务重放不得重复生成或重复释放积分。
- 每笔 A 池入账、B 池冻结、B 池释放和售后冲正均写入关联来源订单、受益会员、规则版本与原流水的不可变演示积分流水。
- 订单状态机至少包含：待上级确认、上级已驳回、待后台审核、后台已驳回、待发货、已发货、已完成、已取消。
- 用户只能在“待上级确认”状态主动取消订单；取消必须记录原因，订单进入不可恢复的“已取消”终态。
- 直属上级只能在“待上级确认”状态确认收款或驳回；后台只能在“待后台审核”状态审核通过或驳回；驳回必须填写原因并进入对应不可恢复终态。
- 后台审核通过、订单进入“待发货”后，用户不能直接取消，只能按售后流程申请处理。
- 已取消或已驳回订单不允许恢复、发货、完成或计入任务；用户如仍需购买应重新提交新订单，原订单完整保留用于审计。
- 取消和驳回只记录业务状态，不在线处理退款；如果用户已经线下付款，页面提示双方在线下完成退款并保留备注/凭证。
- 用户提交订单并在线下向直属上级付款；直属上级在系统内确认已收款后进入后台审核；审核通过后后台可发货并记录承运商和物流单号；用户确认收货后订单完成。
- 发货时按当时生效的后台配置计算自动收货截止时间，默认发货后 7 天；用户可在截止前主动确认，到期仍为已发货状态的订单由系统自动确认收货。
- 用户可从订单发货后开始申请售后，并可在订单完成后的后台配置期限内继续申请（默认 7 天）；一个订单同一时间只能存在一个进行中的售后单。
- 售后支持“仅线下退款”和“退货并线下退款”。用户提交原因、说明和可选图片；后台审核通过时确定处理类型，驳回时必须填写原因。
- “退货并退款”流程为：后台批准并提供退货信息 → 用户填写承运商和退货单号 → 后台确认收到退货 → 直属上级在线下退款并在系统确认 → 售后完成。
- “仅退款”流程为：后台批准 → 直属上级在线下退款并在系统确认 → 售后完成。系统不执行资金退款，只记录退款确认事实、备注和可选凭证。
- 已发货订单存在进行中售后时暂停自动收货；售后被驳回或用户撤销后恢复原自动收货截止规则，到期订单由任务继续处理。
- 售后完成前不新增业绩或积分。若原订单已经完成并产生业绩/积分，售后完成时发布 `AfterSaleCompleted` 事件，通过关联原流水的反向流水冲正，不删除或修改历史流水。
- 已完成订单售后冲正后，原订单对应的升级任务证据失效，并自动重新计算购买人以及该订单直接贡献到的直属上级的当前会员资格。
- 资格重算后不再满足当前等级时，自动降级到仍满足条件的最高等级；若所有升级等级均不满足，则回退到基础会员。降级只影响后续权益，不删除或改写历史等级、积分与业绩流水。
- 自动重算与降级必须幂等且可安全重放；审计记录需包含会员、售后单、原订单、规则版本、变更前后等级、触发原因、执行主体与时间。
- 售后状态转换、退款确认和冲正均使用业务幂等键；重复回调、任务重试或并发操作不得重复退款确认、重复扣减业绩或积分。
- 自动收货天数作为订单快照保存，之后修改全局配置不追溯既有订单；后台可以在发货前调整配置。
- 人工确认与自动确认调用同一个订单完成用例。自动任务使用租约/锁防止多实例重复处理，并以 `SYSTEM_AUTO_RECEIVE` 记录操作者、触发时间和审计来源。
- 只有用户确认收货、订单进入已完成状态后，才发布一次 `OrderCompleted` 领域事件并触发会员升级任务、有效业绩归属和 A/B 积分计算；此前任何状态均不计业绩或积分。
- `OrderCompleted` 事件、会员任务执行和积分流水分别使用稳定业务幂等键；重复确认收货、事件重放或任务重试不得重复升级、重复累计人数或重复入账。
- 系统只记录线下收款确认事实，包括确认人、确认时间、订单应收金额和可选备注/凭证引用；不保存银行卡、第三方支付账号或完整资金账户信息。
- 付款凭证为可选项：现金付款可以不上传；转账付款时用户可上传 1–3 张 JPG/PNG/WebP 图片，每张大小上限由后台配置并设置安全默认值。
- 凭证文件存入私有对象存储，不生成永久公开链接；只有订单所属用户、其直属上级和具备订单审核权限的后台人员可通过短时授权地址查看。
- 图片存储支持通过配置在 S3/RustFS 与本地磁盘之间切换；两种模式复用同一应用端口和元数据模型，商品图片继续通过稳定的应用 URL 交付，私密凭证在本地磁盘模式下仍必须使用短时签名链接且不能暴露真实文件路径。
- 本地磁盘模式的根目录和签名密钥由环境变量配置，文件名、路径穿越、链接篡改和过期访问必须被拒绝；容器部署时上传目录可挂载持久化卷。
- 上传时校验真实文件类型、大小和图片完整性，移除不必要的图片元数据；页面提示用户遮盖与订单核验无关的银行卡号、余额等敏感信息。
- 凭证访问、下载和删除均记录审计；保存期限由后台配置，到期后执行可重试的清理任务，订单中保留文件摘要与清理记录。
- 上级确认、后台审核、发货和收货均使用幂等命令，记录操作者、时间、前后状态、意见/驳回原因和审计日志。
- 商城不创建在线支付单，不接入在线支付、模拟支付或支付回调；订单中的金额仅用于线下应收与审核记录。
- 所有积分均标记为演示积分，不可提现、转账、兑换现金或调用真实代付接口。
- 后端必须提供生产安全联锁：即使修改数据库或配置，也不能启用真实分红付款、自动提现或现金等价物兑换。
- 运营后台可动态配置商品、金额门槛、升级任务、积分规则、资格有效期与审核流程。
- 关键订单、会员升级、关系绑定、积分结算操作必须幂等、可追踪、可审计。
- 技术栈固定为 Spring Boot + MyBatis-Flex + Sa-Token + Redis + Hutool + MySQL + Flyway。
- 后端符合 DDD 分层、限界上下文、聚合与领域事件设计，并遵守项目后续确认的凤凰架构约束。

## Acceptance Criteria

- [ ] 本地可一键启动依赖并运行后端、H5/网页端和运营后台。
- [ ] 新环境按照 README 的单一路径即可启动 MySQL、Redis、私有对象存储、后端、响应式商城和运营后台，并可完成一条端到端演示业务链路。
- [ ] 后端构建、领域单元测试、关键流程集成测试以及两个前端的 lint、类型检查和生产构建全部通过。
- [ ] OpenAPI、架构说明、配置说明、Flyway 迁移说明、演示账号与微信回调配置说明齐全且与实现一致。
- [ ] Flyway 可从空 MySQL 库完成全部建表与基础配置初始化。
- [ ] 用户可注册/登录、绑定邀请人、浏览商品并提交线下付款订单，页面明确提示向直属上级线下付款。
- [ ] 商城首页、商品详情、购物车和结算页形成统一的精品零售视觉系统，真实商品封面优先展示，无封面和图片加载失败均有可访问兜底，并通过桌面与 H5 响应式验证。
- [ ] 微信内 H5 可通过网页授权首次创建账号及再次登录；电脑网页可扫码完成同一流程，并由 Sa-Token 建立商城会话。
- [ ] 同一用户从已关联的公众号 H5 与网站扫码入口登录时进入同一个商城账号；UnionID 暂缺时不会误合并其他账号。
- [ ] 伪造 OpenID/UnionID、篡改或重放 OAuth `state`、重复提交授权回调均不能越权登录、重复注册或改变邀请关系。
- [ ] 除初始化根账号外，无有效邀请链接/二维码的首次微信授权不能创建商城会员；有效邀请可一次性完成会员创建和直属上级绑定。
- [ ] 已失效、已撤销、邀请人无权限或邀请人账号异常的邀请上下文会被拒绝，且不会产生半注册会员或孤立关系。
- [ ] 任何入口均不能自邀、重复绑定、改绑或形成邀请关系环；并发及重复微信回调只创建一个会员和一条关系。
- [ ] 微信密钥和渠道 access token 不出现在前端构建产物、浏览器存储、普通业务日志或 API 响应中。
- [ ] 初始化配置可安全创建 1 个超级管理员和 3 个起盘运营账号，仓库及 Flyway 数据中不存在可直接登录的明文默认密码。
- [ ] 运营账号即使关联超级会员也不会继承或传播后台权限；普通会员无法使用会员登录态访问后台 API。
- [ ] 订单审核、履约、商品、会员和审计角色只能调用各自授权的后台功能，越权请求被拒绝并记录审计。
- [ ] 超级管理员的授权、停用、解锁、关联和凭据重置操作可查询完整操作者、目标账号、前后值、时间与请求来源。
- [ ] 系统不采集银行卡号或第三方支付账户等敏感资金信息，不产生在线支付交易。
- [ ] 用户可以不上传凭证直接提交现金付款订单，也可按限制上传凭证图片。
- [ ] `s3` 与 `local` 两种图片存储模式均可通过配置启动；本地模式可完成商品图上传/读取/删除及私密凭证上传/短时访问/删除，篡改或过期的本地签名链接无法读取文件。
- [ ] 非订单本人、非直属上级和无审核权限的后台账号无法查看付款凭证；凭证不存在永久公开访问地址。
- [ ] 直属上级只能确认或驳回其直属下级的待确认订单，越权访问被拒绝并记录审计。
- [ ] 用户只能取消尚未由上级确认的订单；上级与后台只能在各自阶段驳回并填写原因。
- [ ] 已取消或已驳回订单不能恢复或触发发货、升级、业绩和积分。
- [ ] 上级确认后后台可审核，审核通过后可发货，用户可确认收货并使订单完成。
- [ ] 已发货订单达到自身自动收货截止时间后可被任务自动完成；重复扫描、并发执行或与用户同时确认时只能成功完成一次。
- [ ] 用户可在允许期限内申请仅退款或退货退款；进行中售后会暂停自动收货。
- [ ] 售后完成后，已完成订单产生的业绩和积分通过一次且仅一次的反向流水冲正，原流水仍可审计。
- [ ] 售后冲正导致升级条件不再满足时，购买人及直接受该订单贡献影响的直属上级会自动降到仍满足条件的最高等级；同一售后事件重放不会重复降级或重复冲正。
- [ ] 被降级会员后续再次满足升级条件时可以重新升级，并保留完整的升降级审计轨迹。
- [ ] 系统只记录直属上级的线下退款确认，不调用线上退款或代付接口。
- [ ] 每个订单状态转换均校验合法前置状态；重复请求不产生重复审核、发货、业绩或积分。
- [ ] 待确认、待审核、待发货和已发货订单均不计升级、业绩或积分；只有首次完成订单时计算一次。
- [ ] 满足后台配置的任务后，会员可按流程升级，重复事件不会重复升级或重复入账。
- [ ] 第 6 名及后续符合条件的新会员可按规则快照产生积分池流水。
- [ ] 前 5 名直属新会员只累计资格人数；第 6 名起的默认规则准确生成 A 池 160 可用积分和 B 池 160 冻结积分，重复完成事件只处理一次。
- [ ] 直属上级的符合条件复购订单完成后，B 池按版本化配置和先进先出批次释放；普通购买、未完成订单或重复事件不能释放。
- [ ] 后台修改人数、金额、积分拆分或 B 池释放规则后，只影响新产生的资格证据和积分批次，历史流水仍按原规则快照可解释。
- [ ] 连续无业绩达到配置周期后可自动降级，且任务可安全重跑。
- [ ] 页面、API 响应和后台规则页明确显示“演示积分 / 非现金权益”标识。
- [ ] 项目不存在真实代付、提现和积分兑现金接口；安全测试验证仅修改配置不能绕过该限制。
- [x] 管理员可维护分类、商品、多 SKU、库存、会员、任务与规则，可查询订单/售后详情、凭证和审计流水，并通过权限菜单、安全角色 CRUD 与系统配置完成运营闭环。
- [ ] 核心领域规则具备单元测试，跨层流程具备集成测试。

## Technical Approach

- 后端采用 Java 21、Spring Boot 4.1.x、MyBatis-Flex 1.11.x、Sa-Token 1.45.x、Redis/Lettuce、Hutool、MySQL 8.4 与 Flyway；正式实现先用最小启动模块验证各 starter 的 Spring Boot 4 兼容性。
- 采用 DDD 模块化单体，限界上下文包括 IAM、Customer、Catalog、Trade、Fulfillment、Membership、Distribution、Ledger 与 Operation；每个上下文内部按 interfaces/application/domain/infrastructure 分层，跨上下文只通过显式应用端口和领域事件协作。
- 商城端和运营后台均采用 Vue 3、TypeScript 与 Vite；商城端使用响应式布局覆盖电脑网页与 H5，后台为独立构建和独立路由权限。
- MySQL 保存业务事实、规则版本、状态机、不可变积分/业绩流水、审计与 outbox；Redis 仅保存 Sa-Token 会话、缓存、一次性 OAuth challenge、幂等短锁与任务租约，不作为业务事实唯一来源。
- 凤凰式可靠性通过无状态应用、事务 outbox/inbox、稳定业务幂等键、可重放任务、版本化规则快照、反向冲正流水、租约调度、可观测审计和 Flyway 前向迁移实现。
- 付款、售后凭证与商品素材通过应用层存储端口接入可替换实现；`s3` 模式使用 RustFS/AWS SDK v2，`local` 模式使用受限文件根目录与 HMAC 短时签名交付，任何模式都不泄漏内部对象键或真实磁盘路径。
- 本地环境使用容器编排运行 MySQL、Redis 与 RustFS；后端和两个前端提供统一启动、健康检查、种子演示数据与端到端验证脚本。

## Decision (ADR-lite)

**Context**：截图规则若直接用于真实资金或可提现权益结算存在显著合规风险，但项目需要验证可配置会员任务、邀请关系、积分池和降级机制的技术可行性。

**Decision**：采用“按截图规则制作演示版”。系统可模拟会员升级、人数门槛、第 6 名起计分和 A/B 池流水；用户在线下向直属上级付款，系统仅记录上级收款确认并流转后台审核、发货与收货，代码层不提供在线收单、真实提现、代付或现金兑换能力。

**Consequences**：领域模型会保留可审计规则版本、流水和冲正能力，但真实商业上线必须另立任务，在取得业务地区法律、财税和支付方案确认后重新设计合规边界。
